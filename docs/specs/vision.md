## 1. 为何存在（Purpose）

把本项目从「一个结构良好的 NestJS 模板」演进为「**多租户 SaaS 框架**」：让团队在同一代码库、同一套垂直切片上，以最小成本孵化出**可对外售卖、可水平扩展、租户强隔离**的 SaaS 产品。

- **模板**解决「起步结构」（分层、DI、校验、迁移、门禁）——已具备。
- **框架**解决 SaaS 的根本复杂度：**多租户**（隔离 / 成员 / 配额 / 计费 / 合规）——本愿景的目标。

## 2. 北向目标（North Star）

> **接入一个新租户 = 配置，而非改核心代码。** 一份部署服务 N 个租户，隔离性、身份成员体系、计费用量、数据合规**开箱即用**。

方向性度量（非承诺，落地时转为 `plans` 的完成判据）：
- 租户开通时间（TTHW, time-to-host-a-tenant）趋近于「填表 + 一次迁移」；
- 每新增租户的**边际工程成本**趋近于零（核心代码零改动）；
- 隔离采用**行级（`tenant_id`）**单一策略，不牺牲查询与运维体验（**不做物理 / schema 隔离**）。

## 3. 目标用户与场景（Who）

- **平台 / 产品团队**：以框架为底座快速起一个 SaaS 业务，不自建多租户轮子。
- **租户管理员**（最终客户的运营者）：自助开通、配置、成员与角色管理、用量与账单可见。
- **框架维护者**（我们）：长期演进横切能力，守住隔离与扩展的边界。

典型形态：**B2B SaaS**，以「组织 / 工作区」为租户单元，每租户独立数据边界、配额与有限定制。

## 4. 核心能力支柱（Pillars）

长期方向，按里程碑分阶段（§7）；**须在既有垂直切片模型内扩展，不另起炉灶**：

1. **租户模型与隔离（Tenancy）**：**统一采用行级隔离**（共享表 + `tenant_id`），**不做 schema-per-tenant / db-per-tenant 物理隔离**；隔离靠贯穿的租户上下文 + 数据层强制约束实现。当前基线：Drizzle + PostgreSQL。
2. **身份、成员与授权（Identity）**：Better Auth 由单用户扩展为**多租户身份**——组织 / 工作区 / 成员 / 角色（RBAC），跨租户鉴权边界清晰。
3. **计费与用量（Billing）**：Stripe 从「样例」升为**租户级**订阅 / 计量 / 配额闭环（含用量入账与限流联动）。
4. **配置与扩展（Extensibility）**：领域上下文即插拔；**租户级特性开关与定制**不得污染核心切片。
5. **数据与合规（Data & Compliance）**：租户数据驻留、导出、删除（GDPR/被遗忘权）；操作**审计留痕**。
6. **运营面（Ops）**：可观测（pino）、限流 / 配额、对象存储（S3/OSS/COS）、邮件、i18n——已具雏形，向「多租户可运维」收口。

## 5. 非目标（Non-goals）

划清边界、防范围蔓延：

- **不做**低代码 / 可视化搭建平台；
- **不做** schema-per-tenant / db-per-tenant 等物理隔离（**已裁决：行级为唯一隔离策略**）；
- **不替代**客户领域业务系统——只提供 SaaS **底座 + 横切能力**；
- **不在愿景层锁定**具体云厂商 / 支付商（保持可插拔）；
- **不接受**「能跑就行」的 vibe coding 作为工程标准（严肃性，见 workflow 总则）。

## 6. 设计原则传承

愿景的落地方式继承既有宪法，不新造：

- **架构**：Clean Architecture + DDD + CQRS 垂直切片（[architecture.md](./architecture.md)）；租户上下文（tenant scope）作为贯穿请求的新横切维度，落点在既有 domain/application/infrastructure/api 分层内。
- **工程**：本地 CI 为 L1 裁决、fallow 为 L2 佐证（须二判）、**无已审方案不写码**、完成判据可核验+穷尽（[workflow.md](./workflow.md) · [tooling-standards.md](./tooling-standards.md)）。
- **决策**：权威归人；多租户隔离级别、计费模型等**不可逆决策须人签核**（workflow §3 高危清单）。

## 7. 演进路线（阶段 · 方向非死线）

| 阶段 | 目标 | 关键交付 |
|------|------|----------|
| **0 · 现状** | 模板就绪 | 单租户结构；users / auth / stripe / storage / mailer 为**样例** |
| **1 · 租户域** | 行级隔离跑通 | 租户聚合 + `tenant_id` 行级隔离 + 租户上下文贯穿（请求 scope / DI）+ 多租户鉴权 |
| **2 · 计费与配额** | 商业闭环 | 订阅 + 计量 / 配额闭环；RBAC 完善；行级下的复合索引与单 schema 迁移策略 |
| **3 · 运营与合规** | 自助运营面 | 租户自助管理 + 数据驻留 / 导出 / 删除 + 水平扩展运维 |

> 每阶段的具体方案须落 `docs/plans/`（技术方案）并过**审计门**后方可实现（workflow §1/§3）；阶段推进是 `global` blast radius，须人签核。
