## 工作原则（总则）

> 本章是全流程的**判断依据**；下方操作章节（§1–§7）由其推导。括号内 `P*` 对应来源 `oh-my-env` 立场命题编号。

- **愿景为纲**：一切 `specs` / `plans` 以项目北向目标为纲（见 [`vision.md`](./vision.md)）。
- **决策权威归人**（`P2`）：AI 是事实上的代码编写者与执行者；**判断 / 承诺 / 问责永远归人**——授权可下放执行，不得下放权威（§5）。
- **文档即契约**（`P3`）：`plan` / `spec` = 人与 AI 之间的**授权契约**（授权边界 · 验收标准 · 审计留痕），是唯一 SSOT；**越界即回改契约留痕**，非口头批准（§2/§5）。
- **文档须人主导**（`P7`）：AI 产出 = 候选 / 草稿，经人**理解与选择**后成权威；范围 / 条款 / 验收由人定；「主导」须实质、防名义盖章。
- **无已审方案不写码**（§3）：审计门先于执行；未完成不得关闭 Issue。
- **反馈环优先于理论**：调试先造能对确切症状变红的紧反馈环，**无红环不进入假设**（§6）。
- **机制修复，不逐模块特判**：根因是结构缺陷时修机制 + 补单测，禁启发式掩盖 / 表层补丁；修后双向复测。
- **证据分级（判据链）**：本仓代码 > 实机产物 > 参照源码 > AI 检索引注 > 发现器候选；弱证据只作定位、不产结论（L2 fallow 须二判，§4）。
- **垂直切片 + expand–contract**：一片穿透所有层、可独立验证；宽重构走并存→分批迁移→删旧（§1）。
- **完成判据可核验 + 穷尽**：「每项都核过」>「产出清单」，防 premature completion（§6）。
- **严肃性不随能力浮动**（`P4`）：企业级不得凭感觉、不得不算成本、不得无审慎设计；vibe coding 是现象非方法论。
- **基线是 LLM 能力**（§7）：harness 设计多为「能力相对量」，会随能力提升**溶解**；须分**补偿**（会溶解）与**纪律**（长久），写经验**标注环境假设**。
- **方法论不变、资源调度变**（`P1`）：敏捷 / PM 内核（迭代·反馈·价值排序·风险·验收）继续有效；变的是工具与「AI 是新增开发资源」。
- **多人多 Agent 靠可查共享产物**（`P8`）：归属 / 任务图 / 契约 / 证据 / 门禁，不靠记忆或口头；并行度按**瓶颈**设定（AI 版 Brooks）（§1）。
- **两平面解耦**（`P6`，现阶段缓）：AI 平面与资产平面独立、允许不同步冗余，唯一耦合点 = 授权动作（§8）。

> 本节只立**原则**；具体规则见对应章节，不在此重复（单一 SSOT）。

## 0. 定位与前提

- 本文只定义**流程与文档落点**；具体工具选型/命令一律指针回 [tooling-standards.md](./tooling-standards.md)，防双 SSOT 漂移。
- 面向**有经验开发者**；能固化成**门禁/守卫**的纪律不靠纯文本约定（结构即引导）。
- 本项目**质量门禁走本地 CI**（`bun run ci`），不走远程 CI（GitHub Actions 仅部署 Swagger Pages）——详见 tooling-standards §3/§4.8。
- 现阶段**单文档平面**（`docs/`）；AI 平面（`.ai/`）解耦**暂缓**，见 §8。

## 1. 主流程（一个任务 / 特性）

```
想法 → 确定设计目标 →（需要才）调研(research)
     →（AI 起草）技术方案(plan, 落 docs/plans/) → 审计门 → 无已审方案不写码
     → 实现（垂直切片，逐片可独立验证） → 本地 CI（L1 门禁）全绿 → 完成判据 → PR / 留档
```

- **plan = 方案单位，Issue = 可执行/可认领切片**；一个 plan 可拆多个 Issue（GitHub）；Issue 状态与 plan「执行状态」联动（索引表见 §2）。
- **未完成的内容不得关闭 Issue**——关闭 = 真完成（有证据、过审计）。
- **垂直切片**：一片穿透所有层（domain→application→infrastructure→api，见 architecture.md）、可独立验证、塞进一个上下文窗口；拒绝按层横切。宽重构走 **expand–contract**（并存 → 分批迁移 → 删旧）。

## 2. 文档落点（四区治理）

人/团队平面 `docs/` 分四区，**单向引用、无（已审）方案不写码**：

| 区 | 角色 | 规则 |
|----|------|------|
| `docs/specs/` | 项目宪法 / 长期基准 | **不可突破，但可修订**（修订=重写型，见 §2.4） |
| `docs/research/` | 前期调研 | 只作制定 plan 的**参考，非开发依据**；头部须声明 `用途: 调研参考（非开发依据）` |
| `docs/plans/` | 技术方案 | **开发依据**；带审计与执行状态；完成**留原地、不归档** |
| `docs/recycle/` | 弃用文档 | **只进不出** |

- **现状归类**：`vision.md`（宪法·愿景·顶层）、`architecture*.md`（宪法·结构）、`tooling-standards.md`（宪法·工具）、本文（宪法·流程）属 specs；`event-sourcing-roadmap.md` **已迁至** [`docs/plans/`](../plans/event-sourcing-roadmap.md)（§9.3 已裁决：技术方案非长期规格）。
- **plans 状态单源** 在 [`docs/plans/README.md`](../plans/README.md) 索引表（列：`Plan | 主题 | 审计 | 执行状态 | 关联`）；**文档头不重复标状态**（沿用「单标记防漂移」教训）。
- **`docs/research/` `docs/recycle/` 已预先建立**（§9.2 已裁决）：`research/` 收调研参考（非依据）、`recycle/` 以 `.gitkeep` 占位、只进不出。
- **2.4 specs 修订（重写型）**：正文**整体重写**（不增量补丁）+ **显式变更戳** + **演变过程单列**（§10），三者齐备；`specs` 为「当前真相」，正文 > 演变记录。

## 3. 审计门（无已审方案不写码）

- 方案**须先审计、后依据 / 执行**。审计记录（结论 / 未决项 / 审计人 / 日期）写入 plan 文档头部；审计状态入 §2 索引表。**强制**：即便**单人开发亦不得豁免**（§9.1 已裁决）——深度按 blast radius 分级（全局 / 不可逆=人签核，局部可逆=轻量自审），但**自审仍是必经环节、不得跳过**。
- **深度随 blast radius 分级**（呼应授权粒度 E-001）：
  - 全局 / 不可逆 → **人签核**；
  - 局部可逆 → **轻量自审**（作者对照完成判据自查即可）。
- 本项目**不可逆 / 高危动作清单**（须人签核，不得由 agent 自行执行）：
  1. 数据库 schema 变更与迁移（`drizzle:generate` 产出的 SQL 须人工审 → `drizzle:migrate`；`drizzle:push --force` 仅限 dev）；
  2. 删除依赖 / 删除代码 / 大范围重构（尤其据 fallow 结论者——**必须二次人工核验**，见 tooling-standards §4.7）；
  3. 修改门禁 / CI / husky 钩子 / commitlint / Biome 规则本身；
  4. 修改 `docs/specs/` 宪法条款、公共 API 契约、DI 注入形态（§4.3 陷阱）；
  5. 修改 `.env` / `.env.example` 等**密钥、令牌、连接串**敏感配置（含新增 / 轮换凭证）——须人签核（§9.4 已裁决）；agent **不得自行写入真实凭证**。

## 4. 门禁与工具绑定（工具矩阵 L1–L4）

每层**入口单一、不双轨**；流程各步绑定其工具（命令详见 tooling-standards §7）：

| 层 | 角色 | 本项目落点 | 判据地位 |
|----|------|-----------|---------|
| **L1 裁决门禁** | 合并与否唯一裁决 | 本地 CI（`bun run ci` = check→build→test）+ `.husky/pre-push` + commitlint | **硬门**，任何工具不越此层 |
| **L2 前置发现** | 产出候选供人二判 | `bunx fallow`（dead-code / dupes / architecture） | 参考，**永不裁决**，须二次人工核验 |
| **L3 AI 情报** | 只读取证 / 检索 / 导航 | 暂缓（后续章）；结论须**可引注到源** | 证据可引注 |
| **L4 驾驶舱** | AI 编码工具与配置 | [`AGENTS.md`](../../AGENTS.md)（**统一入口 · §9.5 已引入**）+ `.claude/settings.local.json` | 消费者，**非裁判** |

- **该跑什么**：局部可逆改动 → `bun run ci:quick`（check+test）；提交前 / push → `bun run ci`（full，含类型检查与 fallow 佐证）；涉清理/去重 → 先 fallow 候选 → 人工二判 → 回归。
- **新工具纳入**：先定层、再登记（提案 → 试跑评估 → 定层 → 回写 tooling-standards 矩阵）。

## 5. 授权与决策（模板级轻量约定）

- **决策权威 / 问责永远归人**（P2）；事实查找 / 检索归 agent。
- 二维定档（可逆 × 可验证，E-001）：可逆可验证 → 授权 agent 自动执行（过 L1 即可）；不可逆 / 难验证 → 人签核。
- **越界即回改 plan / 契约留痕**，而非即时口头批准（契约是唯一 SSOT，防授权漂移无记录）。
- 检验信号：人审多为「盖章」→ 授权太细；返工 / 越界升 → 太粗。

## 6. 完成判据（每步须可核验 + 穷尽）

- 判据分两步：**clarity**（能否分辨 done，模糊会诱发 premature completion）+ **demand**（要求多高，驱动 legwork）；最强判据既**可核验**又**穷尽**（「每项都核过」>「产出清单」）。
- 示例：
  - 「迁移完成」= generate 的 SQL 已人工审 **+** migrate 实机成功 **+** `bun run ci` 全绿，而非「跑过命令」；
  - 「fallow 清理完成」= 每条候选已二判（真实修 / 假阳性加 `fallow-ignore` / 存疑留痕）**+** check/test/build/启动冒烟回归全绿（tooling-standards §4.7 步骤）。
- **调试**：先造一个能对确切症状变红的**紧反馈环**（red-capable / 确定性 / 快 / agent 可跑）；**无红环不进入假设**（§5.1 工程纪律）。

## 7. 演进与能力漂移

- 写纪律**须标注环境假设**（本模板当前基线：Bun ≥1.3 / Nest 12 / Fastify 5 / TS 5.9 / Drizzle 0.44，见 tooling-standards §2）。
- 区分**补偿**（随模型/工具能力提升会「溶解」）与**纪律**（任何能力档位都约束行为：人机分工、反馈环、证据链、契约、审计门）。
- 本文本身为重写型：随复盘整体重写受影响章节，不整体重排。

## 8. 边界（本文暂不覆盖）

- **两平面解耦（`.ai/`）**：本轮采**选项 b**（§9.6）——**不建物理 `.ai/`**，改为在各文档头加「**受众**」软标记（`受众:` 字段；约定：`读者: Agent` = 宜注入 agent 上下文，`禁入 Agent 上下文` = 纯人向叙事·讨论·演变；无标签默认人 + Agent），维持单 `docs/` 平面 + `AGENTS.md` 作 L4 入口；将来出现信号（多 agent 并行 / docs 体量拖累上下文成本）再据此平滑拆分到 `.ai/{principles,designs,contracts,records}`。
- **`docs/specs/vision.md`（项目愿景 / 北向目标）**：已**确认定稿**（v0.2.0，含 §6 地域与合规约束）；作宪法顶层，其余 specs/plans 以其为纲。
- **多人 + 多 Agent 编排细节**（归属 / 任务图 / agent↔agent 契约 / 合并门禁）：后续章。
- **skills 层**：本项目暂无可复用 skill（`oh-my-env` 的 baseline-upgrade 属 Odoo 语境，不适用）。
